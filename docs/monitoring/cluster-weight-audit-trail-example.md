# 클러스터 가중치 보정 — 감사 추적(audit trail) 실례

이 문서의 목적은 "③(보정모델)이 ②(프로덕션)보다 점수가 몇 % 높다"를 증명하는 게 아니다 —
[`hit-at-10-eval-report.md`](hit-at-10-eval-report.md)에 정직하게 적었듯, 지금 합성 데이터
규모(50명)에서 순위가 실제로 바뀐 경우는 1건뿐이라 그 주장은 통계적으로 약하다.

**대신 이 문서가 증명하는 것은: 보정값 하나하나가 어디서 왔는지 끝까지 추적 가능하고, 잘못된
값이 들어가도 코드 배포 없이 안전하게 되돌릴 수 있다는 것**이다. "이 가중치 값의 근거가
뭔가?"라는 질문에 대한 답은 "사람이 정했다"가 아니라 "이 공식이, 이 데이터로, 이 시점에
계산했다"이며, 아래는 실제 Supabase 프로젝트에서 그대로 재현한 사례다(2026-08-20).

## 1. 원본 데이터 — 선택 이벤트

`BE:beginner` 클러스터(희망 역할 BE, 경험 수준 beginner)에서 시뮬레이션된 선택 이벤트 3건
(`tests/fixtures/eval_synthetic_selections.json`):

| 이벤트 | 선택된 팀의 beginner_fit | 그 순간 보여준 팀 50개의 beginner_fit 평균 |
|---|---|---|
| 1 | 1.0 | 0.38 |
| 2 | 1.0 | 0.38 |
| 3 | 1.0 | 0.38 |

(실 서비스에서는 이 자리에 `cluster_selection_events`의 실제 행이 들어간다 — BE 연동 전까지는
합성 데이터로 메커니즘만 시연한다는 전제는 변하지 않는다.)

## 2. 계산 — 고정 공식

`app/scoring/cluster_weights.py`의 `compute_weight_lifts()`:

```
lift = 선택된 후보들의 beginner_fit 평균 − 보여준 후보 전체의 beginner_fit 평균
     = 1.0 − 0.38
     = 0.62
```

사람이 "0.62가 적당해 보인다"고 정한 게 아니라, 이 세 줄짜리 뺄셈이 데이터로부터 그대로
산출한 값이다. 코드를 열어보면 이 공식 외에 다른 로직이 없다는 걸 바로 확인할 수 있다 —
정식 ML 모델처럼 블랙박스가 아니다.

## 3. 저장 — Supabase에 남는 기록

`scripts/run_cluster_weight_batch.py`가 이 값을 `cluster_weight_config`에 기록한 실제 행:

```json
{
  "cluster_key": "BE:beginner",
  "component": "beginner_fit",
  "weight_value": 0.62,
  "source": "offline_batch_synthetic_demo_2026-08-20",
  "version": 2,
  "is_active": true
}
```

`source`에 "이 배치가 언제 무슨 이름으로 돌았는지"가, `version`에 "몇 번째 갱신인지"가 남는다
— 나중에 "왜 0.62냐"는 질문을 받으면 이 행 하나로 답이 끝난다.

## 4. 효과 — 실제 추천 점수에 반영됨

`BE:beginner` 클러스터의 실제 유저(fixture user 26)로 라이브 `recommend_teams()`를 호출한
결과(팀 33, `beginner_fit=1.0`인 후보):

| | similarity | role_match | deficit_fit | beginner_fit | activity_style_match | **총점** |
|---|---|---|---|---|---|---|
| 기본 WEIGHTS | 0.40 | 0.20 | 0.15 | 0.20 | 0.05 | **0.875** |
| 보정 후 (beginner_fit lift=0.62 반영) | 0.356 | 0.178 | 0.133 | **0.288** | 0.044 | **0.900** |

가중치 합은 항상 1.0으로 보존되므로(`adjust_weights()`), `beginner_fit`이 오른 만큼 다른
컴포넌트는 소폭 줄었다 — "몰래 점수를 부풀리는" 게 아니라 상대적 중요도만 재분배한다.

## 5. 안전장치 — 롤백 실측

같은 자리에 **의도적으로 극단적인 값(5.0)**을 넣어 "배치가 잘못된 경우"를 재현하고, 실제로
되돌렸다:

| 단계 | `beginner_fit` lift | 팀 33 총점 |
|---|---|---|
| 정상 (v2) | 0.62 | 0.9001 |
| 나쁜 값 주입 (v3, 테스트용) | 5.0 | 0.9368 |
| 롤백 (v2 재활성화) | 0.62 | **0.9001** (정상과 완전히 일치) |

방법: `is_active`를 v3→false, v2→true로 전환하는 것뿐 — **코드 배포도, 서버 재시작도 필요
없다.** v3 행은 `source: "test_bad_value_demo_2026-08-20"`로 명확히 태그해서 지우지 않고
남겨뒀다(실제 배치 산출물과 혼동되지 않게, 그리고 "이런 안전장치가 실제로 검증됐다"는 기록
자체로).

## 요약

| 질문 | 답 |
|---|---|
| 이 숫자(0.62)는 어디서 왔는가 | `tests/fixtures/eval_synthetic_selections.json`의 이벤트 3건 → 고정 공식 |
| 재현 가능한가 | 예 — 같은 이벤트로 배치를 다시 돌리면 같은 값이 나온다(실제로 두 번 돌려 확인) |
| 사람이 임의로 조정했는가 | 아니다 — 공식 외 개입 없음 |
| 잘못되면 되돌릴 수 있는가 | 예 — `is_active` 전환만으로, 실제로 나쁜 값을 넣고 되돌리는 것까지 실측 확인 |
| 지금 효과 크기는 얼마나 큰가 | 작다(50명 합성 데이터 기준 순위 변경 1건) — 크기를 부풀리지 않고 정직하게 밝힘 |
